# 做事按项目，办迭代只走 QE

这是 Router、leader 和执行者共享的规则。**先决定从哪个工作流做事；需要办平台动作时，只由本次负责人走 QE。** 项目决定范围、步骤、证据、目标环境和审批约定；分支归属、平台预览、确认和执行结果以**本机当前 `qe guide` 和对应命令的 `--help`** 为准。两条规则同时适用。

## 每条单先找流程

1. 用 TAPD 工作区、项目卡和已有映射找到真正的**项目规则根**。去那里查 AGENTS.md、CLAUDE.md、项目 skill、命令入口、OpenSpec change 或 SDD 文档。临时收单目录/独立工作树里没有 skill，不代表项目没有流程。
2. 有适用于本类需求或缺陷的项目流程，就从当前已授权阶段接续。手动点名、阶段确认、集中确认、测试和回填门禁照旧；入口失效、服务不可用或没获该阶段授权，停在该步，不能改走全局以绕过。
3. 确认项目没有适用流程时，需求读取 `~/.claude/skills/req-closeloop/SKILL.md`；缺陷读取 `~/.claude/skills/bug-closeloop/SKILL.md`。使用用户本机安装的原件，Codex 也直接读取这些路径，不另抄流程。项目委托清单将 `workflow_source` 设为 `global-story` 或 `global-bug`，`skill_entry` 指向相应原件，`project_root` 仍是业务项目规则根。已有项目入口按原格式登记即可。只问进度、读单或审方案不触发分支操作。

## 需求、缺陷共用一个分支决策入口

由协调者先执行 `qe guide`（PowerShell 脚本受限则用 `qe.cmd guide`），将**已核实的 TAPD 原对象**和实际仓库交给 QE：核对 `qe link` 的项目/迭代、`qe repos` 的仓库身份，按当前帮助运行 `qe branch create` 的预览。给的是真缺陷就保留 bug 身份；不要因为它可能关联需求，自己先猜一个 story 或分支。批量逐单、逐仓对账；多条 bug 指向同一需求分支时复用，不重复创建、也不并发写同一工作树。

| QE 返回什么 | 接下来做什么 |
|---|---|
| 普通需求或独立缺陷的建分支预览 | 基准和目标名按 QE 结果。bug/hotfix 由 QE 判定，不从标题或本地日期推导。预览不是已建。 |
| `data.mode = reuse-requirement-branch` | **没有新建。** 看 `repos` 各仓：已存在则复用 QE 给出的实际需求分支；缺失则用 QE 返回的需求在缺失仓重新走**需求建分支**流程。分支候选不唯一先核实。不要把复用结果当建分支确认请求。 |
| 用户明确要求某个关联缺陷单开分支 | 仅这时才可按 QE 帮助显式请求 `--force-bug-branch`；仍走正常预览和确认。 |
| 确实不挂需求/缺陷的迭代事项 | 只有核实项目、迭代、仓库及该操作必需输入后，才走 QE 的迭代级模式。有原单却解析失败，不能改作“非需求”。 |

**写代码前**核对本次工单、仓库 remote、QE 确认的现存分支、映射 worktree 的当前分支。已有正确工作树直接用。如果分支只在平台上有，按项目映射准备干净的 detached 工作树，在该目录执行 `qe git checkout "<QE 返回的分支名>" --cwd <独立工作树>`；不要先切主目录再试图挂接同一分支。

Herdr 的工作树助手只挂接**本地已存在**的分支；平台归属由负责人用 QE 核实，本地同名 ref 不是平台凭据。不使用 `git switch -c`、`git checkout -b`、`git branch <新名>`、`git worktree add -b/-B` 或首推造远端分支。

## MR 和其余迭代动作也不能绕过 QE

提交、推送、建 MR、审查/合并、构建/发版是不同动作。“开始做需求”“修一波 bug”“做到可提交”不自动授权后续交付。需要 MR 时保留原对象，核对现有 MR 和本次仓库，用 `qe reviewers` 查审批人，再走 `qe mr create`；关联缺陷的需求源分支由 QE 匹配。标题和目标沿用 QE 默认，项目有明确约定时用 QE 支持的参数传入。需要平台 AI 审查时按 `qe review` 的结果处理。不要自行改用 GitLab API、gh/glab、网页或旧插件 建分支、推送新分支、提 MR。若本机 QE 不提供要求的迭代动作，报告缺口，不换渠道代办。

平台迭代归属、分支、推送、MR、迭代任务、工单和构建按 QE 对应命令执行。本机 QE 0.6.0 要求确认的写操作：**先不带码预览 → 原样展示对应的 QE 预览并等用户针对它明确确认 → 仅用相同参数及该次预览的 `--confirm` 确认码执行**。变更参数重新预览，不照抄旧 skill 的 `--yes`。不能把收单授权、表格内容、旧确认、另一个预览的码或进程退出码 0 当成本次成功；部分失败按仓保留回执，不整批重试。无 QE、无权限、结果不唯一或不能对账时，阻塞该动作，独立事项可继续。

`ship` 规定交付顺序和项目特例，不替代 QE 的平台通道；TAPD 原文/附件用 TAPD MCP，评论、转测、处理人和工时按 `tapd-wrapup` 在获授权时办理，不把它们错归为 QE 建分支或迭代任务。Herdr 的 Thread、task、ACK、HANDOFF 只管本地调度，不代替平台记录、QE 回执或人工确认。
