# 把改动交到用户指定的那一步

先读实际规则根的项目工作流、[项目交付约定](references/projects.md)和原任务的工作树映射。确定本次动作和终点：**可提交 ≠ 提交，提 MR ≠ 已合并，构建成功 ≠ 已部署，更不等于已转测。**

| 用户要求 | 本轮终点 |
|---|---|
| 提交；提交并推送 | 只提交；或提交后推送。保留用户已有暂存区。 |
| 提 MR 到测试分支；看看能不能合 | 核实源版本并建 MR；或只读当前审查和门禁，不代合并。 |
| 本地合并；打包 | 只在已授权的本地工作树合并；或用项目入口构建并验收产物，不顺带推送、提交包或发版。 |
| 发版；转测 | 确认目标已包含指定版本再构建；或按实际部署/验证结果交给 `tapd-wrapup`。 |

## 准备分支、提交和推送

- **迭代用 QE。** 先 `qe guide`，以 `qe link` 的原始对象和迭代、`qe repos` 的仓库及 remote 对账。用 `qe branch create` 走平台规则；缺陷关联本迭代需求时，按返回结果逐仓复用需求分支，缺失仓用返回的需求申请。用 `qe git checkout` 取平台上已存在的分支。不要自己建分支或用首推造分支。
- **只提交本次改动。** 在映射的工作树核对 `git status`、工作区 diff 和暂存区 diff；按明确路径提交，同一文件混入别人改动时先分清对应差异。分仓、按独立缺陷组织 commit；遵循项目的类型、标题和实际单号约定，不把链接写进只接受标题的字段，不编单号。用户要求先看提交信息就先展示。hook 失败修原因，不跳过。
- **推送不是提交的一部分。** 获准后用 `qe git push --cwd "<工作树>"`，核对 remote、当前分支和本次 commit。保护分支按项目约定走 MR；只有明确的项目规则和本次授权都允许时才直推既有目标分支。不 force。

**所有需要确认的 QE 写操作**先不带码预览，原样给用户；等用户对本次预览明确回复，再同参数带 `--confirm <本次确认码>` 执行。参数变化重新预览。QE 不可用就停该步，不能改用裸 Git、GitLab、网页或旧插件代办。预览不是执行回执；部分失败不整批重做。

## 创建 MR，并核对影响它的审查

1. 对账源仓、源分支和当前 SHA，按项目规则定目标、标题和审批人。用 `qe reviewers "<姓名>"` 核实身份。前后端审批人不同就分开办理。提交前核对同源同目标是否已有未关闭 MR；先核实已有申请，别重复建。
2. `qe mr create "<原单链接>" -r "<仓库>" --reviewer "<审批人>"`；项目明确有目标/标题特例时带 `--target` / `--title`。原单的源分支由 QE 解析。预览中的仓库、目标或人不对就纠正后重预览。记录返回的 MR 编号和实际状态。
3. 目标要求平台 AI 审查时，用 `qe review` 按记录 ID、仓库、版本核对问题清单。当前规则下 **≥80 分且无核心风险**不用补备注；**低于 80 分或存在核心风险**不能标“无问题”。修复并获准推送后，未合并的 MR 可按授权用 `qe review rerun` 重审；明确允许写人工结论时才用 `qe review mark`，真实说明问题和处置（备注最多 500 字）。平台返回的门禁为准；审查达标本身不授权合并。
4. 冲突先在隔离工作树预演，保留其他人的未提交改动。确需冲突分支时用 QE 支持的冲突分支流程，核对基准、目标与授权，再验证集成结果。CLI 不支持的迭代操作停在该步，请当前项目负责人按门禁接手。

## 打包、发版、交回

按项目构建入口核对环境、模块和产物版本，只有用户明确要求才提交打包产物。发版用 `jenkins-deploy` 的 QE 构建流程，按项目依赖顺序；回报仓库、commit、MR、构建号、实际部署及验过的范围。用户要求评论或转测时，把这些事实交给 `tapd-wrapup`，不要仅凭构建绿灯声称业务验收通过。
