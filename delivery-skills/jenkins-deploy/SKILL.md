# 发哪个服务，测哪个版本

**先分清要查还是要发。** “看构建进度”只查状态；“发版”还要核对项目的发布门禁、目标环境和已合入的版本。打开实际项目规则与发布约定，厘清每个服务是构建依赖、部署入口，还是可以独立发布。

## 从项目名找到实例、job 和参数

```text
qe guide
qe build instances
qe build jobs "<实例>" "<服务关键词>"
qe build params "<实例>" "<准确的 job>"
```

口语别名只是候选，多实例、同名 job 或多个模块时，按环境、folder、服务和仓库核实。以本次应发布的版本为准，比对上次**实际**分支、分支参数名和用户要求；不同 job 可能要求保留或去掉 `origin/`，不能凭经验改写。上次参数不是本次发布授权。需要额外模块参数或指定 folder 时先查看 `qe build run --help`。

## 预览、确认、读回

1. 查询目标提交已在目标分支，按项目约定列出实例、环境、完整 job、分支、模块参数和依赖顺序。准备好独立查询构建状态的方法，尤其是耗时较长的服务。
2. `qe build run "<实例>" "<job>" "<分支>"` 先不带码。把 **QE 的本次预览**原样交用户，明确确认后才用同参数附 `--confirm <本次确认码>`。改目标、分支或参数要重新预览。不能改走脚本或直接调 Jenkins 绕过确认。
3. 记下本次请求的队列/日志凭据、新分配的构建号。用 `qe build status "<实例>" "<job>" --build <本次构建号>`；有本次日志路径可按帮助加 `--log-file`，folder 必须与触发时一致。轮询进程中断先查状态，不重触发。若工具只显示“最近一次 SUCCESS”，还不能认领为本次：按队列、构建时间、job、分支及 SCM 版本对账；查不到就明确写“尚未核实”。
4. 构建结束用确切编号、`building=false` 和实际 result 判断；失败定位本次日志，重试所需修复、推送或再发版各按授权。依赖按项目规定顺序完成，最后的聚合部署或前端分发单独核实；**只构建但未部署的服务不能报已发版**。报告环境实际版本和验证范围，不把发布成功当作业务用例通过。

**运行依赖。** 此 skill 调用本机 `qe build`。首次使用，由获授权的 QE 发行包通过 `qe setup` 安装 Jenkins 驱动和示例配置；按该发行包说明在本机配置实例、folder、分支参数及凭据。不要覆盖已有私有配置，不在代码仓、聊天或日志中回显 token。缺驱动、配置或权限就停止该步，仍可整理已取得的证据。
