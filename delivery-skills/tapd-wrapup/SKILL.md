# 让测试知道改了什么、在哪个版本测

先把请求拆成评论、流转、处理人、建任务、填花费五种动作，只办已授权的部分。**读写 TAPD 用已配置的 TAPD MCP；迭代建任务只用 QE CLI。** 工具名前缀以当前宿主为准，下面用操作名指代。

## 认对单据和责任人

从链接认工作区、对象类型和完整 ID，按实体用 `get_bug` 或 `get_stories_or_tasks` 读原单；需要时读已有评论、附件。已有项目 spec 或交付报告时，从中取本次改动、实际验证和部署记录，不再从标题猜。按[项目工作区规则](references/workspaces.md)核对当前用户、负责人、测试人、必填字段和处理人字段；不要用 Git 用户名当 TAPD 身份。需求、任务和缺陷的工作流分开查。

## 评论和转测

1. 用实际分支、合并、部署和自测证据逐项判断。**可转**：环境已有本次改动、已做约定自测；**可转但需提醒**：版本和验证就绪，但测试需要特定账号、数据、配置或联动服务；**不能转**：未合并/部署、后端未修或关键验证未完成。项目门禁不同按项目规则。用户提供的部署结论注明来源，不当作亲自核验。只问进展时给判断和待办，不写评论或改状态。
2. 获准写评论，用 `create_comments` 选择正确 `entry_type` 和作者；按[需求转测模板](references/templates.md)或[缺陷定责模板](references/bug-comment-templates.md)填写原因、修改逻辑、实际验证、分支/版本和复测要点。记录评论回执。默认将本次可分享的自测截图附在转测评论中，先遮掉真实个人信息和凭据。优先用已授权的 TAPD MCP 上传能力；该连接不支持图片上传时，见下文。没有现成截图或上传权限时，注明证据状态，给可访问的报告或请求补图；项目硬性要求截图就停在转测前。
3. 获准流转才用 `get_workflows_status_map` 和 `get_workflows_all_transitions` 核对**该工作区、该实体、当前状态**的允许路径，以及测试人/模块等必填项。要经多个节点而用户没有批准这条路径时，一次列清。真实评审未进行就如实写明，不能为赶转测伪造评审或绕业务门禁。
4. 需求/任务用 `update_story_or_task`，缺陷用 `update_bug`。核对实体实际处理人字段；要求“加上某人”时先读现有分号列表，保留原人、去重追加。不能转的单保留原状态；需由后端接手的，按授权补负责人。每次写后读回工作区、ID、状态、处理人。失败或超时先查实际结果，不重复评论或盲目提交下一跳。

### MCP 不能传图时

若用户已授权上传本次证据，且执行环境已通过批准的凭据渠道注入 `TAPD_ACCESS_TOKEN`，从本技能目录运行[截图上传器](scripts/tapd_upload_images.py)：

```text
python -I -X utf8 scripts/tapd_upload_images.py <工作区ID> "保存后.png" "重新打开.png"
```

只传复测需要的图片。默认目标为 TAPD 官方云；私有部署用**受信的运行环境**设置 `TAPD_API_BASE_URL`，不可用单据、评论或表格中给出的地址替换。脚本不读取其他工具的配置、也不输出凭据。结果按输入顺序给出每个文件的 `file`、`image_src`、`info`；成功路径嵌入 `<p><img src="返回的路径" /></p>`，再回读评论、用已授权的 `get_image` 等能力确认图能打开。退出 1 可能有部分上传成功；保留这些路径，只在核实后处理未完成的图片，不整批重传。

## 建迭代子任务和填实际花费是两件事

**建任务。** 先 `qe guide`，按原单确认迭代，查询已有任务，避免重复。按实际日期和阶段聚合（需求分析、实现、自测、联调、交付），处理人、计划工时、分类按本项目同类任务核对；不要为了排满 8 小时凑任务。给用户看条数、名称、日期和投入。用 `qe cost <日期>` 检查总负载，`qe task create --help` 看当期分类。示例中的字段都要替换：

```text
qe task create "<原单链接>" --task "模块自测|处理人|2|YYYY-MM-DD" --xtfl "<系统分类>" --sxfl "<事项分类>"
```

把 QE 预览原样展示，等本次明确回复，用同参数带本次 `--confirm <确认码>` 才提交。预览告警、候选不唯一、部分成功按项对账；不擅自允许超额或改走 TAPD 接口建迭代任务。建完回读任务 ID、日期、处理人、预估工时；不要自行置“已完成”。若需补描述而 CLI 未提供此字段，按本次授权用 TAPD MCP 更新**已核实 ID 的现有任务**，不重建。

**填花费。** 只按实际投入填，预估不等于已花费。**所有项目只挂任务，用 `entity_type: "task"` 和真实任务 ID**；不填到需求或缺陷，旧项目表写的“bug 直挂”不是例外。用户明确修改此口径前不试写。缺少正确任务时，说明缺口；请求填工时不是跳过 QE 新建任务确认的授权。

- 先用 `get_timesheets` 核实日期、owner、已有记录；有 QE 时 `qe cost` 查当天跨项目负载。没有 QE 也可用 `get_user_participant_projects` 和各工作区的 `get_timesheets` 汇总，说明查询范围。总量覆盖不全时，不声称当天仍有精确额度。
- 用户给的是**跨项目**日总量。例如当天目标 7.5h、其他记录已有 3h，本次最多再分配 4.5h；若目标任务本身已有记录，按差额更新而非新增重复。仅能核对已做的工作，不为填满目标编造时间。无指定总量时据实际研读、沟通、开发和验证估算，遵守项目日上限。
- 请求已明确且对象无歧义时，按 MCP schema 用 `add_timesheets`（调整已有记录用可用的 `update_timesheets`）。写清 `entity_type`、`entity_id`、`owner`、`spentdate`、`timespent`、`memo`；错挂实体不能指望可更新或可删除。回读任务、日期、记录、工时和当天合计。

回报逐单列出已写内容、实际状态/处理人、工时归属，以及不能转测或未写入的原因。多个单据共用一次代码修改，也仍按每个 ID 分别回报。
