# 让接收人拿到就能做下一步

先确认**给谁、要他完成什么**。已经有缺陷台账、接口记录或需求 spec 时，从里面取事实。涉及多方就拆成面向不同读者的段落，不把技术排查史发给产品。

| 接收人 | 这次交什么 |
|---|---|
| 后端 | 接口、脱敏请求、实际字段与期望字段、期望依据、页面影响、修完如何复验。可直接粘贴成 TAPD 评论草稿。 |
| Python / 算法 | 调用时机、输入输出字段表（含类型、必填、单位）、一对请求响应样例、需要确认的差异。 |
| 产品 | 用页面语言描述待决问题、选项和推荐理由。Excel 每行一件事，留「产品决定」「备注」两列给对方填。 |
| 外部对接方 | 新旧接口或字段的差异、双方各改什么、哪一项需要对方确认。 |
| 测试 | 将修复版本和环境、前置角色及数据、复测动作和预期、仍未验证的情形写在一起。 |
| 聊天中随口问 | 给一段可复制的纯文本；手写「1）2）」编号，转发时也能保留。 |

每条问题都能单独转发：写上对应页面、工单或样例定位信息；区分「已复现」「根据现有证据推断」「待确认」。若没有足够证据，列出接收人需补的字段，不编造原因或替产品选定口径。准备请求样例时使用合成或脱敏的业务值；认证由接收人在自己的授权环境里提供，不复制真实令牌、Cookie 或账号。

[按接收人选择模板](references/templates.md)。用户只要粘贴文本，就直接给文本；需要文件时优先沿用项目交接位置，否则放在 `.scratch/handoff/`，以日期、主题和读者命名。HTML 做成独立单文件；Excel 首行冻结、长文本换行、待填列用浅黄色，生成后回读行数与字段。生成评论草稿与实际发评论是两个动作；只有明确要求回写时，才走已配置的 TAPD 收尾流程。
