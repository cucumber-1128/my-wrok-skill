# 需求闭环（轻量 SDD）

一页 spec 解决三件事：**验收有清单、交付有留痕、转测评论和填花费有素材**。既可以先写后做，也可以在代码完成后用它对账。

## 第 0 步：找项目、分档

**项目**：优先用会话中已配置的项目资料库、项目卡和工作树绑定。否则用环境变量 `WORK_SKILLS_LIBRARY` 指向本机私有资料库（下文称「资料库」），按 `映射.json` 的仓库路径最长前缀找项目，核对 TAPD 工作区与实际规则根。配置缺失时仍可先读需求；需要持久化 spec 时再确认一个业务仓库之外的私有目录。已确认项目但资料库尚未建档，可将 spec 放在资料库的 `_未归档/需求/`。

| 情况 | 做法 |
|---|---|
| 真实规则根中有适用项目流程（如项目 skill、OpenSpec change、AGENTS.md 指定的入口） | 接续项目原阶段，不另建 spec。需要人工审批或入口故障时停在原阶段，不能因堵塞改走全局 |
| 小改动（文案、单字段、单按钮，改哪里很明确） | 获准实施后不必建 spec，直接修并真机核对；如获准回写，再把结论留在 TAPD |
| 中等及以上 | 建 spec，按下面两个入口之一走 |
| 用户只说「看下详情 / 读一下」 | 拉需求、评论、图片展示，问一句要不要做，不自行开工 |

## spec 放哪

- `<资料库>/<项目>/需求/ID<TAPD 后 7 位>-<关键词>/spec.md`，没有单号用 `<YYYYMMDD>-<关键词>`。沿用资料库中的模板，没有则用[一页 spec 模板](references/spec.md)。
- 截图等证据放同目录 `evidence/`。
- **不写进业务仓库**：不放 `.scratch/`，不改仓库里的 CLAUDE.md。
- 一个需求跨多个会话时，新会话先读 spec，看「状态」字段接着做。

## 入口 A：先写后做

用户给了需求链接，还没开始写代码。

1. **读全**：TAPD MCP 取需求正文、全部评论、附件，正文和评论里的**每一张图都用 `get_image` 打开看**，图和旁边的文字一起理解。TAPD 图多是粗糙截图标注，默认按图意改造，对齐现有组件和文案规范；产品明确说「就按这个样子」才像素还原。
2. **对照代码定锚点**：结合项目卡，找到要改的文件、组件、接口。
   - 按文档改造时，先比对文档和代码现状；文档描述的改动已经存在，就停下来问是哪一期。
3. **写 spec 前三节**（状态 = 起）：
   - **要做什么**：一句话复述这波改什么，**按字面范围**。文档外的「优化点」不进 spec，最多在交付说明里写一行。
   - **验收标准**：每条都是能在页面或接口上看到的现象，写成 `- [ ]`。
   - **改动点**：仓库 / 文件 / 改什么。
4. **待确认**：有就一次列完问清楚，等答复后写进 spec；没有就写「无」。只要求方案时在这里交回；已授权实施且没有项目停点，再进入开发。
5. **实现**（状态 = 做）：涉及迭代先读本机 `qe guide`，将 TAPD 原单交给 QE 判断并核对目标仓，只在确认的分支和映射工作树实施，不自行用 Git 建分支。需要新建时，先展示 QE 本次预览、等用户确认后再执行。方案变了同步改「改动点」；计算、过滤、状态判断等纯逻辑按 TDD 补测，UI 拼装和样式不硬写单测。
6. 做完进入下面的「验收」。

## 入口 B：先做后补（最常用）

用户已经自己写完了，说「做完了 / 收个尾」。

1. **收集**：读全 TAPD 需求（同入口 A 第 1 步）；看本需求分支相对基准分支的改动：`git log` 和 `git diff <基准>...HEAD`，基准用项目卡里写的集成分支或 `git merge-base`。涉及多个仓库就每个都看。
2. **反推 spec**：「要做什么」和验收标准从需求来，「改动点」从 diff 来。两类对不上的单独列给用户：
   - 需求里有、代码没改到的：可能漏做；
   - 代码改了、需求里没有的：可能超出范围，或者是顺手修的。
3. 进入下面的「验收」。

## 验收（状态 = 验）

- **环境和登录**：从私有项目卡查目标环境及已授权的登录方式。测试环境使用配置好的登录助手；预生产、生产由用户登录，生产只读取证。服务日志、数据库、隧道等仅用已有授权的项目入口。不要把凭据写入 spec、截图或评论。
- **浏览器**：遵循项目指定的浏览器及本机的 `browser-routing` 规则。需要登录态或内网时用已授权的会话，纯本地页面用项目支持的测试浏览器。
- **逐条验**：每条验收标准都按页面操作走一遍，页面和网络请求都对才勾选；把结果和证据（截图路径、接口路径与关键字段）写进「验收记录」。没验的不勾，写清原因（缺数据、缺账号、等后端）。
- **发现问题**：
  - 前端问题直接修，按 bug-closeloop 4a 的标准修，修完重验这一条；
  - 后端问题交接到字段级：接口、脱敏入参、实际值、期望值及依据、复验步骤；有 `handoff-doc` 时用其「给后端」格式。记进「待确认」，不在前端打补丁兜底。
- 不能用 mock 代替真机验收；数据确实造不出来时，先说明原因，征得同意再 mock。

## 交付（状态 = 收）

- 推送、MR、构建等迭代操作只走 QE：需要写入时先展示预览，等用户确认本次参数后再按帮助执行；参数有变，重新预览。QE 不可用就停在该步，不改走其他通道。
- 提交、推送、合并请求、发版分别按 `ship` 的顺序和本次授权执行；每做完一步，把分支、commit、MR 编号、构建号补进 spec 的「交付」。迭代任务走 QE，TAPD 评论、转测、处理人、工时交给 `tapd-wrapup`，用真实验收结果作为回写素材。
- 做完说一句「下一步通常是 X」，等用户发话，不自动往下走。

## 回写项目卡

本次发现可复用的启动方法、角色前提或验证注意事项，补进私有 `项目卡.md`，保持 ≤60 行。环境条目只记录批准的配置来源和使用条件，不把密钥写进项目卡。

## 收尾回报

```markdown
| 需求 | spec | 验收 | 下一步 |
|---|---|---|---|
| 示例：增加筛选条件 | 本次 spec 路径 | 5/6 通过，1 条等接口提供样例 | 接口就绪后复验剩余项 |
```

另外列出对不上的项（漏做、超范围）和给后端的说明文件路径。
