# Bug 定责闭环

每个 bug 都走同一条路：**先拿证据分清是谁的问题 → 前端的修好并真机验证 → 后端的写清楚交出去 → 在 TAPD 留下结论**。用户要的不是"把数字改对"，而是责任清楚、修复可信、别人看评论就知道发生了什么。

## 让位规则

- 按用户已绑定的 TAPD 工作区、项目资料库或 `WORK_SKILLS_LIBRARY` 下的 `映射.json` 找**项目规则根**。有适用的项目级缺陷流程，就接续原阶段及其审批，不另起本技能的修复线；项目暂时受阻不等于没有流程。
- 用户只要求「看下详情」：拉详情 + 评论 + 图片展示即止，问一句要不要处理，不自行修。

## 第 0 步：接入与台账

| 输入 | 处理方式 |
|---|---|
| 单个/多个缺陷链接 | 保留 workspace 和完整缺陷 ID；例如从 `tapd_fe/<workspace_id>/bug/detail/<bug_id>` 取身份，再用 TAPD MCP 对照原单 |
| TAPD 缺陷列表页（带筛选条件） | 用 MCP 核对明确的范围、处理人或状态；若不能还原用户的选中项，请补充逐条链接或导出清单，不将整个迭代当成这次的任务 |
| Excel 缺陷清单 | 只读指定 sheet/行的链接，按 workspace 和完整 ID 去重，保留未识别行。记住来源位置；不执行宏，状态回写前先确认 |
| 口述/截图/文档 | 整理成「现象 + 复现步骤 + 环境 + 账号来源」 |
| 别的项目的 bug（「看看这里有没有同样的问题」） | 先在当前仓库确认是否存在同一缺陷，存在再走闭环 |

**批量（≥2 个）时**：按「优先级 > 严重程度」排序，在项目批准的私有工作目录建 `bug-<批次关键词>/triage.md`；不要把真实缺陷台账和截图推到公共仓库。

```markdown
| # | Bug | 标题 | 优先级 | 定责 | 证据摘要 | 状态 | commit | TAPD 回写 |
```

台账的作用：批量 bug 常跨多次压缩和多个会话，新会话读台账就能接着做，最后的汇总也从这里出。用户中途追加 bug（「新加了几个」）就追加行继续做。

## 每个 bug 的闭环

### 1. 读全

用 TAPD MCP：`get_bug` + `get_comments`（含流转备注）+ `get_entity_attachments`，正文和评论里的**每一张图都用 `get_image` 打开看**。

> 使用当前宿主配置的 TAPD MCP 命名空间。**读缺陷/需求不要开浏览器**；浏览器用于复现取证和真机验证。评论里常有测试补充的复现条件，或后端已经回复的结论——先读懂回复，再判断前端是否跟改。

### 2. 复现取证

- **环境**：先查项目启动技能和私有项目卡，确认要复现的服务、版本与环境。账号、内部入口和客户专属的环境笔记保留在本机，生产只读取证。
- **登录与浏览器**：用项目规定的浏览器及本机 `browser-routing`。测试环境走已配置的登录助手，预生产和生产请用户登录；需要已有登录态时用授权会话，一个 bug 从头到尾用同一浏览器。
- **抓真实请求**：记录页面对应接口（编号/路径）、入参、响应里的关键字段值。这是定责的证据，也是后面写评论的素材。

### 3. 定责

| 结论 | 判断依据 |
|---|---|
| 前端 | 接口返回正确，页面展示/交互/传参错 |
| 后端 | 接口返回的数据、计算、过滤、分页本身就错 |
| 配置/数据 | 菜单、模板、字典、采集定义、SQL 未执行等 |
| 环境 | 未发版、代理/VPN、服务没起、缓存 |
| 非缺陷 | 需求理解不一致，需要产品拍板 |

请求参数正确、页面忠实展示、但服务返回值仍违反已确认的契约时，交给后端定位，前端不打补丁兜底。例如契约要求一个比率，接口却固定返回占位值；页面把它乘以 100 并不能修复计算。写清契约依据和实际请求；口径未定或证据不足时先标待确认。

**需要写代码时先落实分支**：负责人读 `qe guide`，将 TAPD 缺陷原单和目标仓交 QE 判断。关联本迭代需求时按 QE 返回的各仓结果复用需求分支；有仓缺分支，针对 QE 返回的需求为该仓申请。独立缺陷由 QE 判断分支类型。只在经核实的分支和映射工作树上改，不用 Git 自建分支。推送、MR 等迭代动作也只走 QE；需要确认的操作先展示本次预览、等用户明确回复，参数变更重新预览。QE 不可用时停在该步，不用其他工具绕过。

### 4a. 前端问题 → 修复 + 真机验证

- 最小改动修复根因。同一根因在别处也有的一起改（用户常说「所有 xx 相关的地方都这么改」）；根因不同的范围外问题列出来问，不顺手改。
- 纯逻辑（计算、过滤、格式化、状态判断）按项目的 TDD 规则补单测；纯样式和交互不硬写单测。
- **真机验证**：在浏览器里按 bug 的复现步骤走一遍，页面和网络请求都对才算修好。不能用 mock 代替；数据确实造不出来时，先说明原因，征得同意再 mock。
- 修完报告：改了哪些文件、根因一句话、验证怎么做的、看到了什么。

### 4b. 后端问题 → 字段级说明

按 `handoff-doc` 的「给后端」格式交接；未安装时写齐这些字段即可：接口编号/路径、复现所需的脱敏入参、实际字段值、期望值及依据、影响页面、可重放的测试请求。认证值用占位符。这份内容同时用于 TAPD 评论和发给后端的说明。

### 5. 提交

只在用户说「提交」时提交。**一个 bug 一个 commit**，只暂存相关改动，按项目约定写 `fix:` 和真实缺陷标识。推送、合并请求、发版分别按 `ship` 和本次授权办理。

### 6. TAPD 回写评论

- 这一轮用户说了「评论/回写/闭环/写到 tapd」就直接发；没说就把评论草稿列出来，确认后再发。
- **已修复的也要评论**（问题原因 + 修复逻辑）：测试和后端都靠这条评论判断改了什么。
- 通过 `tapd-wrapup` 回写实际缺陷，`entry_type=bug`，按本机配置核实 TAPD 身份与工作区；HTML [评论模板](references/comment-templates.md)可直接复用。
- 评论只写结论和证据，不写排查过程中的试错。

### 7. 交接

转测、补处理人、填工时 → `tapd-wrapup`；推送、合并请求、发版 → `ship`。在回复里说清下一步是什么，等用户发话。

## 节奏

- 批量时连续推进「定责 → 修复 → 自测」，不必每个 bug 都停下来问；需要用户的事（登录、口径拍板、范围外改动、是否兜底）攒在一起问。
- 遇到阻塞（等后端发版、等产品确认）在台账里标状态，接着做下一个。

## 收尾汇总

```markdown
| Bug | 定责 | 状态 | commit | 下一步 |
```

状态取值：已修复待提交 / 已提交 / 后端处理中 / 待产品确认 / 环境问题 / 非缺陷。给后端的说明文件路径一并列出。用户要求时，把状态回写到原 Excel 清单。
